# iOS 移动端连接生命周期与同步增强设计

## 范围与基线

2026-11-23，基于 `main` 的当前代码。本设计只针对 iOS App（`Xagent-IOS`），
Android 端共享同一套 Flutter 连接代码，按同一设计分阶段跟进。
不更换 DSH 通信协议，不重写 Noise 加密、Relay、P2P、Mux、seq 增量事件机制。

设计目标一句话：**即使底层连接断开、切换、被系统挂起，用户的会话、任务和操作
状态仍然连续可靠**——不追求物理连接永久在线，追求逻辑会话持续在线。

## 现状与问题定位

现有数据面质量不低：端到端加密到位（Server 只转发密文），增量同步协议严谨
（snapshot 游标 + 严格连续 seq + 缺段 `session/page` 补齐 + 重连 resync +
assistant revision 防丢）。缺的是移动端系统级能力。

| 问题 | 优先级 | 影响 |
| --- | --- | --- |
| 锁屏期间的关键事件缺少提醒，回前台后的状态补齐与可操作时间未验证 | P0 | 后台时收不到关键事件，回前台等待不明 |
| 聊天记录无本地持久化（仅内存 `ChatRowsCache`） | P0 | 打开会话依赖 Host 在线与网络 |
| 重连路径未经实测，首次建连耗尽与交接行为未知 | P0 | 需先验证再决定是否改造，不预设重写 |
| 回前台恢复路径存在但耗时未实测 | P0 | 用户感知恢复慢，需分阶段计时 |
| 无系统级通知（任务完成/审批/失败） | P1 | 后台时收不到关键事件 |
| 游标去重依赖 seq 单调前提，跨日志代际未验证 | P1 | Host 日志重建复用 seq 时可能跳过新内容 |

已确认可复用的既有能力（本设计不重复建设）：

- `session/prompt` 已携带 `requestId`（uuidV4），接口约定同一 ID 重试幂等，
  成功应答代表指令已进入 Agent 收件箱。客户端已具备发送幂等请求的能力，
  但 Host 端去重记录能否跨重启保留需另行验证。
- `ConnectionDiagnostics` 已记录 phase/step/attempt/attempt/network（RTT、
  connectDurationMs、fallbackReason、iceProtocol），缺的是各阶段耗时分解。
- 增量同步的 gap repair 与 resync 机制完整，缺的是把 `_lastSeq` 游标从内存
  搬到本地存储，并在跨进程恢复复用前确认本地历史与 Host 日志能够衔接。

## 设计原则

1. **Local-first 渲染**：界面展示不依赖实时网络。打开会话先读本地库即时展示，
   后台异步连 Host 增量同步刷新。
2. **Host-authoritative 同步**：电脑端始终是业务数据权威来源，本地库是缓存，
   冲突以 Host 为准。
3. **Connection-independent 会话**：业务会话生命周期独立于物理连接。连接断开、
   重建、路径切换对用户透明。
4. **正规 iOS 后台能力**：不绕系统。不用无声音乐、伪 VoIP、高频静默推送、
   高频后台任务做保活（审核风险 + 电量）。APNs 只做事件驱动通知，不做心跳。

## 模块划分

新增或改造四个模块，保留现有架构：

| 模块 | 职责 | 主要落点 |
| --- | --- | --- |
| Connection Lifecycle Manager | 连接状态审视、重连路径实测、前台快速恢复、网络变化即时验证 | `relay_backend.dart`、`tunnel_carrier.dart` |
| Local Store | 本地持久化消息、会话、同步游标、outbox | 新增 Drift 数据层 |
| Sync Engine | 游标恢复、事件补偿、事务一致性 | `session_api.dart` `_SessionWatch` 扩展 |
| Notification Dispatcher | Host 关键事件 → APNs 分发 | Server 签发 + App 原生桥接 |

## 一、连接生命周期管理

### 1.1 重连路径审视（评审修正）

现状（已对照源码核实）：首次建连与既有连接恢复分别有重试路径。`RelayHostLink._run` 的退避循环（Backoff 1s→30s、最多 8 次）只作用于首次建连，取得 client 后循环结束；既有连接掉线后由 carrier 驱动 mux 自驱恢复，旧 attempt 的回调有代际检查（attempt 不符即丢弃）。两阶段交接时是否有重复握手、首次建连耗尽后如何恢复，仍需实验验证，不是已确认的根因。

动作：先做重连路径审视与实测，不预设状态机重写。两类故障分开判定：

| 判据 | 方法 | 指向 |
| --- | --- | --- |
| 一次恢复中有时间重叠的建连尝试 | 计数连接建立至登录完成期间重叠的建连时间窗口 | 并发合并（single-flight） |
| 重试预算耗尽后能否再次建连 | 真机断网异常后恢复网络，观察能否触发新一轮建连 | 预算策略是否过紧 |
| 重试预算是否足够 | 统计后台下建连失败次数分布 | 退避参数是否需要调整 |

只有确认存在并发重叠才做 single-flight 改造；耗尽问题则调整预算或触发条件，不整体重写状态机。

### 1.2 心跳、超时与主动探测（评审修正）

现有三层检测分开描述，触发条件与作用不同，不共用同一个超时语义：

| 层 | 触发 | 实际行为 |
| --- | --- | --- |
| 传输层 Relay 心跳 | 无帧输入持续心跳间隔的 3 倍 | 该路径判定死链并断开；默认 25s 仅为兜底，实际上限由握手协商，不是写死的检测上限 |
| 业务层健康探测 | 每健康间隔检查近期是否有入站数据 | 有入站数据则跳过本次探测（现状依据），探测超时默认 10 秒，不是 1–2s |
| 回前台主动探测 | 回前台 kick() | 直接探测，并发探测合并（_probing 判空） |

改造目标：重连退避保留 0.5–30s 封顶 + jitter；用户操作触发重连立即掐断退避。心跳与探测参数先保持现有协商值，待真机弱网实测后再调。「有入站数据则跳过」可以保留，但需结合传输层心跳的独立检测，避免慢链无业务数据时也没有任何强制探测。

### 1.3 传输路径优化（后续研究，不是本轮 P0）

现有实现明确规定：数据 socket 断开即连接结束，Noise 状态从不沿用跨连接，新连接会替换同设备旧连接。因此「热切换仅换数据通道、加密会话与流全部保留」是当前无法兑现的承诺，不再写入设计。

拆为两件：
1. 优先建立可用路径：Relay 快速建连、直连后台协商。先实测直连协商是否拖慢了建连恢复，再决定是否调序。
2. 已有连接无缝迁移：跨端可行性研究，先以换网后自动恢复同一业务会话、消息连续为通过标准，底层允许重新握手。

## 二、本地持久化（Local Store）

技术选型 SQLite + Drift。数据库配置文件保护，密钥用 Keychain 管理，退出账号
清除缓存。现有 `ChatRowsCache` 保留为 UI 渲染缓存，不再是消息的唯一客户端缓存。

### 2.1 表设计

| 表 | 内容 |
| --- | --- |
| `hosts` | 主机信息、最后在线状态 |
| `sessions` | 会话标题、类型、任务状态 |
| `messages` | 用户消息、Assistant 回复 |
| `session_events` | Tool Call、工具结果、审批、状态事件 |
| `sync_cursors` | 每个会话最后持久化 seq、assistant revision、日志代际 |
| `outbox` | 尚未确认送达 Host 的操作（requestId 为主键） |
| `attachments` | 文件/图片本地缓存索引 |

### 2.2 打开会话流程

现状：打开 App → 连接 Host → 拉 Snapshot → 解析构建消息 → 显示。

目标：打开 App → 读本地 SQLite 即时显示 → 后台异步连 Host → 游标恢复 + 增量
同步刷新 UI。电脑关机、手机无网时可读已同步历史。

## 三、持久化增量同步（Sync Engine）

不新增协议参数。现有 `session/follow`（snapshot + 事件流）+ `session/page`
（throughSeq/beforeSeq 分页）+ gap repair 逻辑正确，缺的是游标持久化，
以及跨进程恢复时先确认本地历史与 Host 日志能够衔接再复用游标。

流程与现有实现对齐（不是先补页再订阅，那样补页期间产生的事件会落在两者之间）：

打开 session/follow → 接收首帧快照 → 在同一订阅内按缺口用 `session/page`
补页 → 按序处理后续事件帧 → 事件与游标同事务提交 → 更新 UI。

一致性要求：

- 事件写入与游标更新同一数据库事务。
- 去重键：Host ID + Session ID + 日志代际 + seq。代际只在同一代日志内有效；确认日志重建后，为新记录建立独立的本地代际，不与旧记录共用 seq 命名空间。身份尚未核实时，先保留旧记录，按 §3.1 分页校准，不直接覆盖。
- Replay 与 live 订阅之间不留遗漏窗口（补页发生在同一 follow 流内）。
- assistant revision 同样持久化。
- 会话删除、Host 日志清理能正确同步。

### 3.1 游标续传的前提与风险（评审修正）

seq 游标去重依赖一个未验证的前提：**同一 Host 的同一会话 seq 单调、不重用**。
Host 日志重建（崩溃恢复、日志清理、Host 重启后日志重置）可能复用相同 seq——
手机存到 seq=100，Host 重建后也到 100，数字相同内容可能完全不同，旧游标
会把新内容判为已见而跳过。客户端本地的 followEpoch 只证明「同一次订阅的
回调」，不证明「Host 日志没重建」。

因此只有能确认属于同一代日志，或有足够重叠记录可以核验时，才复用旧游标
续传。无法确认时，先展示 Host 已确认的范围，再分页校准历史。注意**局部
快照不能覆盖整库**：快照有消息数量上限（当前默认 500 条），直接拿它重建
整段本地历史，会丢掉快照范围外的旧记录。离线首屏（local-first 渲染）可以
先做，跨重启续传放在其后。

### 3.2 本地删除的触发条件（评审修正）

会话没出现在本次 resident 列表，不能据此认定已删除——Host 可能只是暂时
没有该会话的投影。只有 Host 明确返回删除事件，或明确的权威查询结果（如
会话列表接口确认不存在且返回码明确），才触发本地删除。本地库中「不在列表」
只标记为 stale，不删数据。

`afterSeq` 类的新协议字段是优化不是必需项，Host 不改协议。

## 四、可靠消息投递（Outbox）

Host 端幂等已有客户端约定：`session/prompt` 携带 requestId，接口约定同一 ID
重试幂等，已接收的用户消息会在 `source.rpcId` 回显请求 ID。但该约定能否跨
Host 重启保留、保留多久，在 iOS 仓库内无法单独证明。

因此 outbox 把原请求的目标账号、Host、会话、内容和 requestId 全部落盘，
恢复后按原请求 ID 对账：在权威历史中找到对应消息，标记为 Host 已收件；
暂时查不到则保留「待确认」，不自动重发。跨 Host 重启自动重发，单独以去重
验证为前提。有时效性的操作（权限审批、取消任务）重连后先校验对应任务/审批
状态仍有效才执行。

## 五、APNs 通知系统（P1）

事件驱动，不是心跳。链路：Host 产生关键事件 → Notification Gateway → APNs →
手机。推送载荷不自动享有 XAgent 业务通道的端到端加密，因此只带通用提示和
不透明事件标识，详情仍走加密链路拉取，正文不进推送。Apple 也不保证每条
远程通知送达，漏推不是验收的阻断项。

| 事件 | 推送策略 |
| --- | --- |
| Agent 正在输出 token | 不推送 |
| Agent 完成任务 | 可见通知 |
| Agent 请求权限 | 高优先级可见通知 |
| Agent 等待输入 | 可见通知 |
| Agent 执行失败 | 可见通知 |
| 普通会话状态变化 | 合并后静默推送（仅限有限唤醒做增量同步，不做保活） |
| Host 上下线 | 按用户设置 |

工程要求：token 更新、设备解绑、通知去重、开发/生产环境隔离。
落点：Server 签发推送凭据（Xagent 仓库）、App 注册 device token 上报（Xagent-IOS）。

验收分三项：①服务端能记录 APNs 是否接受请求；②收到通知后能直达正确会话；
③即使漏推，回前台仍能找回待审批事项。

## 六、可观测性

在现有 `ConnectionDiagnostics` 基础上补各阶段耗时分解，让"连接慢"可定位：
WebSocket 建立 / Noise 握手 / 直连协商 / Relay 转发延迟 / Host RPC 响应 /
snapshot 数据量 / UI 渲染，各自独立指标。不新建整套 tracing，扩展现有结构。

## 八、验收指标

初始工程目标，不是当前实测数据。恢复耗时分三类分别测：复用旧连接的热恢复、
重新握手的冷建连、Host 离线时只验本地历史可读。用户能感知的恢复分三步，
指标计到「可发送或审批」为止，不是计到 WebSocket 建连为止：

| 指标 | 目标 |
| --- | --- |
| 本地历史消息首次展示（离线） | ≤200ms |
| 回前台看到旧聊天（复用旧连接） | ≤200ms（读本地库） |
| 回前台看到电脑最新进度（Host 在线，指定网络条件） | P95 ≤2s（游标恢复 + 缺段补齐） |
| 回前台可发送/审批（Host 在线，复用旧连接） | P95 ≤2s |
| 回前台可发送/审批（Host 在线，重新握手） | P95 ≤3s |
| Wi-Fi/蜂窝切换后可发送/审批 | P95 ≤3s（允许底层重新握手） |
| Host 离线时查看历史记录 | 支持，显示明确状态提示 |
| App 被系统杀死后恢复会话 | 支持 |
| 断线后历史同步 | 优先增量，不重复全量传输 |
| 用户指令重复执行 | 幂等测试中为 0 |
| 已持久化事件丢失 | 故障恢复测试中为 0 |
| 关键任务状态通知 | 三项验收：①服务端记录 APNs 接受结果；②收到后能直达正确会话；③漏推时回前台仍完整同步 |

故障测试场景（需真实 iPhone，模拟器不反映后台挂起与系统回收）：锁屏 30 分钟
解锁后自动同步；后台 24 小时历史可读且自动恢复；进程被杀冷启动恢复；Wi-Fi→5G
切换不重复执行；进电梯保界面不清数据；电脑休眠提示 Host 不可达；电脑重启校验
会话状态；Server 重启客户端自动恢复；Agent 长任务不因手机断线受影响；发送指令
时断网不丢失待确认状态；Agent 输出中断网恢复后补齐缺段；万级事件会话分页读取；
多设备并发操作最终一致；推送未送达时回前台仍完整同步。

## 边界

- 不重写 Flutter 客户端为原生；iOS 系统能力走原生桥接。
- 不改 DSH 线协议，不加新 wire format；`session/prompt` 幂等、`session/page`
  分页、`session/follow` 语义保持不变。
- 不采用绕过系统的保活手段（无声音乐、伪 VoIP、高频静默推送、高频后台任务）。
- Android 端共享连接代码与数据层设计，按同一阶段跟进，不在本设计内实现。
